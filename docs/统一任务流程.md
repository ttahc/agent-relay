# 统一任务与协作流程

本增量基于 v0.4.2；版本号未变，不代表已部署或已发布。窗口申请和环境资源域的独立待合并工作不在本增量内。

## 创建时选择完成方式

- **审查后完成**：默认值。旧任务以及省略 `completion_policy` 的旧客户端保持原有规则。`review_mode` 继续独立决定指定人员、不同窗口或不同责任账号审查。
- **执行者完成**：新任务使用 `completion_policy: executor-direct`。执行者封存交付后逐项提交真实产物和检查说明，记录为“执行者完成，未做独立审查”。没有伪造人工或独立验收。

策略在创建后冻结，执行者和范围编辑均不能降级。需要不同策略时建立明确的新任务。项目资源、能力、可见范围、并发和来源规则保持不变。

直接完成不是进程停止：动作或资源未确认结束时只能留下完成声明，不能归档。实际停止、物理占用清理、全部领取结束后，当前仍获授权的原完成者可自行归档；也可由原指定接收者依既有权限归档。完成者被撤权后不保留写入授权。

## 已完成任务的问题与返修

已完成或缺证收口任务详情有“完成后复查”入口。报告时提交现象、复现条件、证据或明确待补内容。问题固定绑定原 `close_id`、接受记录、范围、领取、修订和 manifest 指纹。

当前项目管理员或指定接收者可以记录补证、确认需修改、复查已解决或问题不成立。解决结论需重验所指交付的实际载荷。结论说明实际复核人及是否参与原交付，不把所有复核标为独立审查。

确认需要修改后，项目管理员可创建关联返修任务：

1. 原任务、原交付、原收口和旧领取保持原样。
2. 记录指向原结论的更正，并原子地建立一个新的返修任务及问题关联。
3. 返修继承原资源和执行边界、保留原冻结输入，附上并优先展示新的返修说明与判据。创建者可以明确勾选将最近完成返修的交付（首轮为原已接受交付）分享为新任务的项目可见输入，供另一执行者读取；默认不扩大原产物权限。新任务默认等待核对与发布，有新的领取、执行代次和资源申请。
4. 返修完成不自动关闭问题。问题处理者核对新返修交付后记录解决结论。

同一问题不会因重试或并发重复建立返修任务。再次发现不同问题可新增问题；关闭问题的重开必须先记录新增证据。上一返修已经完成后，可在新证据确认需修改时新建下一轮返修；历史返修及其完成证据保留。下游依赖不会因报告问题自动失效或重启。

受限问题只能由提交者与管理员查看，不能直接生成项目可见返修任务。需要返修时，先登记不含受限内容的独立项目问题，避免自动扩大传播范围。

## 反馈当前、延期和历史

反馈按当前、延期、历史分区，原始证据与处理记录始终保留。分区取决于反馈本身状态，关联任务关闭不会自动关闭或重新打开反馈。

- `resolved`（问题已解决）：关联任务已完成，且有复现条件与解决证据，不要求编造改善指标或经验。
- `verified`（已验证关闭）：保留原严格要求，仍需实测前后指标、证据、经验和适用限制。

关闭后重开有版本检查和新的处理依据，历史不被覆盖。

## 沟通与可选经验

任务详情和项目中提供“沟通与经验”。沟通支持提问、说明、阻塞、结论和请求复查，可以指名接收人、回复同任务消息。

“已收到、已回复、已执行、已办结”都是用户明确登记的沟通事项状态。查看、通知、普通文字或沟通办结都不等于任务验收，不授权执行，不授予资源。

经验必须引用任务或反馈，填写适用条件、方法、证据和局限。它是可选候选产出。当前有项目管理权限的人员可在核对来源当前版本后确认或退役；AI 管理身份和受托权限不能代替人员确认。确认后内容不原位改写，变更可新建候选并退役旧条目。

搜索先检查来源可见性再匹配内容。受限反馈形成的经验不会扩散到整个项目；消息、经验及复查记录在审计和事件投影中也保留来源权限边界。

## 接口和兼容

所有写入继续使用认证、稳定 `request_id`、持久回执和单写账本。恢复请求仍复核当前身份、权限和版本。

- `POST /v1/executor-complete`：领取、代次、范围、修订、manifest SHA、逐项检查；可选 `finish: true` 只在已经实际停止且无资源占用时尝试归档。
- `POST /v1/close`：符合直接完成条件的原完成者或原审查流程授权接收者归档。
- `POST /v1/task-issue-open`、`task-issue-review`、`task-repair-open`。
- `GET /v1/post-completion?task_id=...`。
- `POST /v1/task-message`、`task-message-status`、`experience-save`、`experience-state`。
- `GET /v1/communication?project=...&task_id=...&q=...`。

`features` 提供新增能力标志。`wait` 可返回沟通和完成后问题变化的稳定事件标识，客户端仅提示并读取详情，不自动执行动作。积压沟通不会挤掉资源或执行提醒；超过单次事件上限时返回 `more-events` 提示补读，其指纹覆盖全部可见事件，避免静默漏变更。

旧 schema 仍按原语义读取；只有使用新增语义时才提高 `min_reader` 到 7。执行安全 schema 仍是 5，不能据此降低安全要求。旧程序会拒绝载入新语义，而不是静默误读；后续安全迁移不降低读取下限。

本分支不包含尚未合并的执行环境与资源域功能（PR #19）。读取下限 7 不表示理解该分支的读取下限 6：没有实际域执行能力时，会拒绝下限为 6 或包含其环境表、冻结物理证明的数据。后续组合两项功能须保留双方规则、读取下限取最大值，并重跑资源冲突、撤权和任务流程检查；不能只修改版本数字。

## 验证

使用 Python 3.13+ 执行 `python -B run_checks.py`。专项入口：

- `verify_feedback_sections.py`
- `verify_direct_completion.py`、`verify_direct_completion_ui.py`
- `verify_post_completion.py`
- `verify_task_communication.py`、`verify_workflow_client.py`
- `verify_workflow_integration.py`

最后一项使用真实 Service、HTTP、稳定重试和服务重启，必须在项目支持的本机 ext4 或 Windows NTFS 上运行。可用 `TASKPOOL_VERIFY_TMP` 指向合格存储。环境资格或 socket 限制表示未验证，不能算通过。页面结构回归不等于实际浏览器视觉验收。
