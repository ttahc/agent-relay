# 运维与升级

适用于 v0.3.0 候选及后续兼容版本。本文给出当前代码具备的运维接口和操作边界，不表示本机已完成安装、正式切换或原窗口验收。人员网页流程见[人员手册](本轮优化操作.md)，客户端恢复见[AI 客户端手册](AI客户端操作.md)。

## 当前部署与发布核对

部署范围为本机 WSL Podman，目标容器为 `intranet-task-pool-local`。Windows 继续使用已核对的 HTTPS 转发、网卡范围和证书；DHCP 或证书变化后重新核对实际入口、服务名和指纹。本文不要求修改现有 TLS 私钥或冻结合同。

构建使用 `python -B build.py`，WSL 可用 `python3 -B build.py`。正式切换前先完成候选构建、所需定向检查和独立环境验证，记录完整镜像 ID、构建包 SHA256、固定源码版本、检查结论与未验项。完整包为 `dist/task-pool-local.zip`，AI 最小包为 `dist/taskpool-ai-client.zip`。本地提交不构成异机备份。

应用版本与内部数据合同分别编号。旧 schema 2 升级说明和内部 v3 名称是合同阶段记录，不应作为当前人员登录或重新初始化现有卷的指引。日常账号页已移除历史身份迁移表单，系统管理员在运维工具中按需显式展开；正常窗口处置从窗口管理办理。

v0.3.0 R2 以 security 4／5 记录安全语义：4 为内部 A 安全边界，5 为完整执行配置／段／动作／资源协议。A 不单独投产。普通服务在 schema 3／4 上须先完成受控迁移；未知更高语义拒绝读取和写入。旧程序遇首个不可忽略的 security effect 应 halted；实际旧服务与旧 CLI 的隔离验证仍须记录，不能只以文档当作通过。

## 就绪与本机维护控制

`GET /readyz` 和 `HEAD /readyz` 为匿名只读探测。运行态返回 HTTP 200 和 `phase=running, ready=true`；维护阶段返回 HTTP 503、`ready=false` 及 `Retry-After`。该接口只说明能否接收新的业务请求，不能证明任务已经停止、资源已经释放或版本已经验收。

维护控制连接已运行服务的私有本机 Unix socket，并核验受限控制密钥，不通过另开第二个 Service 修改账本。在目标容器内使用：

```sh
python -B /app/taskpool.py upgrade-control status
python -B /app/taskpool.py upgrade-control drain
python -B /app/taskpool.py upgrade-control freeze --timeout 30
python -B /app/taskpool.py upgrade-control cancel
```

需要指定存储名时，全局 `--store local` 放在 `upgrade-control` 前。`status` 只查询状态；`drain` 暂停新领取、返修开工和新的自动开工；`freeze` 等待已经接收的请求结束，再关闭新的业务读写准入。超时会取消排空、回到运行态并返回失败，不能将失败当作已经冻结。`cancel` 恢复请求准入。

`shutdown` 是受控退出动作；正常版本切换由下述脚本处理目标容器的停止和启动，避免只退出应用后被容器重启策略自动拉起。以上动作不终止外部 AI 或程序工作，不替代持有者的实际停止回报，不改领取代次和真实资源占用。

## 运行指标（/metrics）

`GET /metrics` 以 Prometheus 文本格式给出运行数字：服务阶段、账本条数、本次读取账本的耗时、各状态任务数、无人持有的开放任务数、活动领取数、超时与失联提醒数（按种类）、已登记窗口数与在线数、等待连接占用与上限，以及启动以来写请求（所有 POST）的次数、总耗时和最长耗时。指标只含数字，不含任务标题、身份名称、路径或令牌。

读取须带抓取令牌。服务运行时也可以生成，不写账本，不需要停服：

    python -B taskpool.py --store local metrics-token

命令只输出一次令牌，库内的 `metrics-token.json` 只保存它的 SHA256；再次运行即替换旧令牌。抓取时以 `Authorization: Bearer <令牌>` 提交，系统管理员令牌同样可用。来自本机回环地址的请求也须带令牌：WSL 的局域网端口转发会让外部连接看起来来自回环地址。

## 同进程一致性备份与定时安排

已选方案是**本机私有定时备份，异机目标后配**。计划由 WSL 专属 systemd timer 调用目标容器的同进程备份入口。该入口短暂冻结业务写入，使用现有 Service 锁和同一 SQLite 连接生成一致性快照，完成或失败后恢复进入备份前的阶段；不停止容器，也不另开活动账本写者。

```sh
podman exec intranet-task-pool-local python -B /app/taskpool.py upgrade-control backup \
  --archive /backup --tag "<唯一备份编号>" --timeout 30
```

执行前须确认容器把指定的本机私有目录挂载到 `/backup`，目录权限、容器用户映射和可用空间正确。备份编号每次唯一，不覆盖旧清单。具体 timer 名称、触发时间、挂载路径和首次实际成功记录由安装记录确认；代码和文档存在不等于定时任务已经启用或异机复制已经配置。

每个完整快照包含文件清单及 SHA256 引用，SQLite 使用备份接口取一致视图；不可变对象按 SHA256 增量保存并去重。需要同时保留清单和被引用的对象，不能只复制一份清单作为完整备份。备份内容含私有服务数据，应放在受限目录；不要作为发行包、普通附件或 Git 内容提交。

`--timeout` 只限制排空等待；进入 `backing_up` 后继续拒绝业务请求，控制客户端另留 300 秒响应宽限，不能通过中途取消维护恢复写入。备份成功或失败后服务恢复原来的 `running` 或 `draining` 阶段。回执不明时先核对状态和原编号清单，不要用新编号盲目重复发起。清单同时记录账本位置与指纹；目标位于原存储目录内部或其祖先、存在符号链接、或编号已经使用时会拒绝。

完整快照覆盖 `local` 目录，并对白名单同级 `tls/key.pem`、`tls/cert-v2.pem`、可选 `tls/cert.pem` 单独保存 `service_files`。清单的 `tls_backup` 明确 complete／incomplete／absent；只有私钥和至少一份证书均已包含才是完整 TLS 身份备份。源和目标拒绝符号链接，私有根目录为 0700、对象为 0600。公开证书不能替代私钥，私有备份不作脱敏发行材料。

服务启动时固定 `service-config.json`，记录实际端口、主机名与别名、TLS 路径、数据／备份范围及可用的启动配置摘要，不含私钥内容或原始令牌。普通完整快照还须有 `configuration_backup.status=complete` 和对应配置对象。

```sh
python3 ops/verify-backup.py --archive /var/lib/taskpool-backups --tag <原编号>
sh ops/install-local-backup.sh
```

`verify-backup.py` 核对完整 TLS、配置记录、repo／凭据／请求日志、固定 head 对应的全部账本事件，以及每个对象的存在、普通文件性质、大小、权限和 SHA256；只输出清单 basename、文件数与 head。缺 TLS、缺配置、对象损坏或只有 seed 时不能宣布完整恢复点。

专属安装器以 WSL root 检查固定容器 `/backup` 挂载及根目录 0700、10001:10001，安装 `local-backup.sh` 与必需的同目录 `verify-backup.py` 到 `/usr/local/libexec`，再安装应用专属 service/timer。日程为香港时间每天 03:30，错过可补一次，同实例互斥；不自动删除快照，也不处理异机目标。安装和首轮实际成功回执分别登记，本文不表示已启用。不得省略 verifier 只安装 shell 入口。

## 离线备份工具

`ops/backup-store.py` 是独立的受限备份工具，参数如下：

```sh
python -B ops/backup-store.py \
  --store "<local目录绝对路径>" \
  --archive "<私有备份目录绝对路径>" \
  --tag "<唯一备份编号>"
```

最终快照要求原服务写者已经退出，并取得 `service.lock` 和 `service-writer.lock`；活动写者存在时工具拒绝执行。加 `--seed` 可在服务运行时仅预存不可变材料，它不生成完整一致性快照，不能将成功 seed 当成已完成备份。当前定时安排使用前节的同进程控制通道，不应定时对活动卷直接运行此工具的最终备份。

WSL 私有归档目录使用 700 权限，安全升级脚本将其映射给 Podman 用户命名空间中的服务 UID 10001。读取或导出时使用合适的 `podman unshare` 身份；不要通过扩大目录权限解决访问问题。恢复前应在隔离位置核对清单、引用对象、SHA256 和数据库一致性，保留原卷及原备份。

## 安全迁移与单写切换

`ops/safe-local-upgrade.sh` 只切换已经构建并完成隔离验证的本机兼容镜像，不负责拉取、构建、代码提交或自动恢复旧数据。调用参数为：

```sh
sh ops/safe-local-upgrade.sh \
  "<完整候选镜像ID>" "<唯一升级编号>" \
  "<私有备份目录绝对路径>" "<隔离验证回执.json>"
```

回执至少包含与候选完全对应的 `image` 和 `verified: true`；镜像字段为完整 SHA256 镜像 ID，不能只写浮动标签。源码、候选包、候选镜像和回执必须属于同一次验证。

脚本在停服前从经过核对的原容器 inspect 固定私有不可变 `<升级编号>.launch.json`，保留原 Cmd、端口映射、卷、用户、TLS 路径、主机名／别名（含 `taskpool-host`）、环境、重启策略和安全设置；通过 argv 重建，不拼接 shell 启动字符串。启动配置只报告摘要，不打印环境中的私有值。新实例收到 `TASKPOOL_LAUNCH_CONFIG_SHA256` 并记录到服务配置。原 `/backup` 绑定不同于本次私有根时拒绝，不能顺手更换站点、证书或网络。

常规顺序为固定启动配置、在线预存不可变材料、排空、冻结、只停止目标容器、完整冷备份核验、新镜像独占迁移，再按原配置启动候选。停止使用无限等待，避免超时升级为 SIGKILL；不重启 Podman machine，不并行运行两个同卷写者。

脚本的迁移命令形状如下，由已停止服务后的独占新镜像执行，不在活动同库旁再开一个写者：

    python -B /app/taskpool.py security-migrate --target 5 --request-id migrate-<升级编号>

内部按 3→4→5 幂等检查点处理。无法确认的旧未决请求保留证据并隔离待受权恢复，不按新含义盲目重放；不能清空旧请求日志来绕过检查。切换前须准备并隔离验证能理解目标 schema 的维护恢复镜像／入口。

**首次从 v0.2.0 升级**时，旧版本尚无上述控制和持久网页会话，必须明确追加 `--legacy-v020`。这次会有短暂停服，原内存网页会话无法恢复，人员须重新登录；账号密码和窗口私有凭据仍需分别核对。不能将后续持久会话支持描述成首次升级无感或零停机。

旧版冷备份没有新 `service-config.json`。仅此首次路径可由 `verify-backup.py --allow-legacy-config <同档案升级编号.launch.json> --launch-config-sha256 <停服前固定摘要>` 核对独立启动配置；仍要求 TLS 和全部原数据对象完整。这不是日常定时备份的例外，后续日程默认严格要求配置记录。

后续兼容版本可保留已持久化且仍在有效期内、未因改密或撤销失效的网页会话；实际效果仍须用同一浏览器核对。已有任务的领取、代次、未结回执及占用应在切换前后逐项比较，不能只看健康检查。

## 失败、请求与回退

冻结未完成时，不启动候选写者；确认自动取消或用控制接口取消维护，先处理仍未结束的请求。离线快照失败时保留原数据，脚本可重新启动原容器；该过程不通过旧快照覆盖当前卷。

边界提前到 **security-migrate 首次尝试**：该命令可能已经提交 security 4，即使迁移未完成或新 HTTP 尚未启动，也不能自动启动 v0.2.0、并行旧写者或覆盖旧备份。保留当前卷、新日志、旧容器和冷备份，使用理解 4／5 的维护入口只读诊断、继续幂等迁移、补回执或受控导出；修复后以前滚恢复正常写入。当前工具不提供自动全卷恢复。只有此前已经证明没有新语义或新业务写入，才可取消切换恢复旧实例。

所有业务写入使用稳定 `request_id`。回执不明时使用原身份、原操作、原编号和原内容查询或重试；相同编号配不同内容会被拒绝。网页提交前的就绪探测能在已知维护或连接失败时保留原页面，但探测后仍可能发生切换；已发出却丢回执的请求不能靠另建编号自动解决。

开始许可、实际开工、完成事实和物理安全归还是不同记录。draining 期间不发行新许可，但已有许可的 started／结果回报属于事实，按受限入口接收。默认没有自动结束确认适配器；本机文件／隔离工作树的身份核对不证明外部进程已停止，外部程序的自动检测与自动归还未启用。运维控制也不替代这些证据。

## 管理员离线恢复与待验记录

管理员全部登录方式丢失时，先停止同库服务，按维护要求使用本机授权入口 `taskpool.py admin-recover --request-id <唯一编号>`，交互设置新密码或使用受限密码文件。核对新回执后恢复正常准入。不要在服务仍持有写锁时再开启第二个 Service，也不要将密码放入命令行、正文或普通日志。

服务内探针、源码检查、隔离备份检查和候选镜像不能代替原环境验收；真实切换、同一浏览器会话、待处理请求、私有定时备份首轮成功及异机恢复验证分别登记。
